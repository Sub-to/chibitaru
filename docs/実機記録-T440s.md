# T440s 実機での実測（2026-08-23）

ThinkPad T440s / Core i7-4600U (Haswell, 2013) / RAM 11.4GB / USB 3.0 起動
→ 8g プロファイル

## VM では確かめられなかったもの

| | 結果 |
|---|---|
| GPU | Intel Haswell-ULT Integrated Graphics |
| VA-API ドライバ | **i965 2.4.1**（3つ入れて libva に選ばせる方式が的中） |
| H.264 デコード | **Main / High とも VAEntrypointVLD で有効** |
| zram | 4GB・優先度100 |
| noatime | 有効 |
| swappiness / page-cluster | 150 / 0 |
| earlyoom | 稼働中 |

**2013年の Haswell でも動画は GPU に降りる。** mpv 採用の前提が実機で
裏づけられた。

## 待機時のメモリ（実機）

```
TUI シェル      35 MB
端末            17 MB
labwc          100 MB
pipewire        19 MB
sshd             8 MB
その他+kernel  822 MB
────────────────────
合計          1001 MB / 11658 MB = 9%
```

VM では 595MB だったが実機は 1001MB。差の大半は「その他+kernel」で、
実機は本物のドライバ（無線・GPU・音声・USB）を抱えるぶん増える。
VM の数字は下振れすると考えたほうがよい。

## 実機でしか出なかったバグ

**① /opt へのインストールが抜けていた**
autostart は `/opt/chibitaru/bin/chibitaru-session` を起動するのに、
setup.sh はそこへ何も置いていなかった。画面が真っ黒になった。
VM で見逃したのは、検証スクリプトがリポジトリを /opt に手でコピーして
から setup.sh を流していたため。**テスト側が本番と違う前提を作って
穴を塞いでいた。**

**② USB 上にスワップ領域があった**
Debian インストーラが既定で作る。zram が優先されるので普段は
使われないが、逼迫時に USB へ書き込みが流れる。USB 起動時は
swapoff して fstab からも外すようにした。

## 作業中に踏んだ落とし穴（実機のコンソール）

- **sudo が入っていない** — インストール時に root パスワードを設定すると
  sudo は入らない。`su -` で回避。エラーが日本語でダイヤ化していたため
  気づくまで時間がかかった。
- **コンソールに日本語フォントがない** — システムのメッセージも
  setup.sh の出力も全部ダイヤになる。`export LANG=C` で英語にすると読める。
  **コンソールで動かすスクリプトを日本語で書いたのは設計ミス。**
- **コンソールでは日本語を入力できない** — 実機に打たせるコマンドは
  英数字だけにすること。
- **長いパスの手打ちは失敗する** — `/root/.ssh/authorized_keys` の
  手打ちで空白が混入し3回失敗した。スクリプト化して打つ量を減らすのが
  唯一の対策。
- **wpa_supplicant が Segmentation fault で落ちる** — Debian 13 の
  この版で。有線か Android テザリングで迂回した。未解決。

# 内蔵 SSD へ移行（2026-08-23）

Crucial MX500 500GB（内蔵）へ、動いている USB システムをそのまま複製した。
インストーラを起動し直していない。設定もテーマも済んだ状態が移った。

`bin/chibitaru-to-disk` として道具にしてある。

| | |
|---|---|
| 起動方式 | レガシー BIOS（grub-pc） |
| 構成 | MBR + ext4 単一パーティション（ラベル chibitaru） |
| 複製量 | 4GB / 所要 約1分 |

## 起動が 36.7 秒 → 4.0 秒になった

移行直後の起動が異常に遅かった。

```
修正前   kernel 32.9s + userspace 3.9s = 36.7s
修正後   kernel  1.5s + userspace 2.5s =  4.0s
```

userspace は速いのに kernel だけ長い、という形だった。`dmesg` の
時刻を追うと、ルートをマウントする直前に**31秒の空白**があった。

原因は `/etc/initramfs-tools/conf.d/resume` が USB 上のスワップ領域の
UUID を指したままだったこと。その領域は USB 対策で無効化済みなので、
initramfs が存在しないものを探して 30 秒待ってから諦めていた。

`RESUME=none` にして initramfs を作り直すと解消した。スワップは
zram（メモリ内）にしかないので、休止からの復帰先はそもそも存在しない。

**教訓**: スワップを止めるときは、fstab だけでなく復帰先の設定まで
面倒を見る。片方だけ直すと、症状が起動時間という遠い形で出る。

## 実機で見つかった setup.sh の抜け（この移行で）

- **sudo が入っていない** — Debian のインストーラは root パスワードを
  設定すると sudo を入れない。パッケージに追加し、対象ユーザーを
  sudo グループに入れるようにした。
- **/usr/sbin が PATH にない** — `shutdown` が見つからない。
  `/etc/profile.d` で通した。開発中に自分が 4 回踏んだ罠でもある。
- **`--update` が無かった** — 内蔵へ移したあとに USB 側で修正を続け、
  内蔵が取り残された。作り直さず差分だけ送るモードを足した。

# 動画再生の実測（2026-08-23）

1080p H.264（Big Buck Bunny サンプル）を同じ画面で再生して比較。

## メモリ — 設計どおり、むしろ良かった

| | メモリ(PSS) | プロセス |
|---|---|---|
| mpv（GPUデコード） | **115 MB** | 2 |
| Firefox（同じ動画） | **475 MB** | 9 |

見積もりは mpv 180MB だったので、実測はそれより軽い。
差は 360MB で、4GB 機なら搭載量の 9% にあたる。
**「動画は mpv に逃がす」という判断はメモリ面で正しい。**

なお Firefox の 475MB はローカルの動画 1 本だけを開いた状態。
ウェブページを開けばこれに上乗せされる（3タブで 800MB を実測済み）。

## ハードウェアデコードは効いている

mpv が `Using hardware decoding (vaapi)` を出すことを確認した。
2013 年の Haswell でも 1080p H.264 は GPU に降りる。

ただし libva は最初に iHD（Gen8以降用）を試して失敗し、i965 に
落ちてから動いている。動くには動くが毎回エラーを吐くので、
setup.sh で実際に試して動いたドライバを `LIBVA_DRIVER_NAME` に
固定するようにした。**PCI ID の表は書かない。試して決める。**

## 消費電力 — 主張を撤回する

設計書に「mpv なら発熱と消費電力が下がる」と書いていたが、
**この測定では裏づけられなかった。**

| | CPU パッケージ電力 | CPU秒/10秒 |
|---|---|---|
| 待機 | 0.80 W | - |
| mpv（GPUデコード） | 14.43 W | 1 |
| mpv（CPUデコード） | 16.96 W | - |
| Firefox（同じ動画） | 5.44 W | 6 |

- GPU デコードと CPU デコードの差は **6% しかない**。
  デコードよりも 1080p を画面に描く処理のほうが支配的。
- mpv は Firefox より **CPU を 1/6 しか使わないのに電力は 2.6 倍**。
  この矛盾は説明できていない。描画面積・フレームの出し方・
  10 秒クリップのループ再開など交絡が複数ある。

**分かっていないことを「省電力です」と書かない。** 電力については
きちんとした実験（同じ窓の大きさ・長いクリップ・複数回）をやり直す
まで、設計書から主張を落とす。メモリの根拠だけで mpv 採用は十分成立する。

## 計測で危うく間違えたこと

最初の Firefox 比較は **Firefox が再生していない状態**を測っていた。
`file:///tmp/test.mp4` を開いてもダウンロード確認が出るだけで、
10 秒間の CPU 使用が 0 秒だった。「Firefox の方が省電力」と
報告する寸前だった。

`<video autoplay muted>` の HTML を用意して再生させ、CPU 時間で
本当に動いているかを確かめてから測り直した。
**測る前に「それは本当に動いているか」を確かめる。**

# Phase 3 の実測（2026-08-23）

## 音声入力

| | |
|---|---|
| whisper.cpp | v1.7.4 を T440s 上でビルド（base モデル 142MB） |
| 速度 | 11秒の音声を **5秒**で書き起こし（実時間の2.2倍速） |
| 常駐 | **0MB**（呼んだ時だけ動く） |
| マイク | ALC3232 / 音量 40% で 声 RMS 1527・頂点 11568（割れず） |
| 聞き取りの門 | 380（声 1527 と 環境音 93 の相乗平均） |

2 コアの 2013 年 CPU で実時間より速い。音声メモとして実用になる。

### whisper は雑音から文章を作る

環境音だけの録音に対して、括弧つきの注釈 `(音楽)` だけでなく、
**「これがシンクとかのヴァインスとか、なかなかというの」** という
普通の文に見える架空の文を返した。文字列の除外では防げない。

対策は 3 つ重ねた:
1. 音量（RMS）の門を機体ごとに測って置く
2. whisper の信頼度の閾値を厳しくする（-nth 0.3 -lpt -0.5 -et 2.0）
3. **Vault に書く前に見せて確認を取る**

3 が効く。押して録る使い方なら利用者は目の前にいるので、
一度見せて決めてもらえばよい。

### 音割れの真因は ALSA 側だった

pipewire の音量を下げても直らなかった。ALSA の Capture が
+28.5dB で増幅しており、**ADC の段階で既に波形が潰れていた**。
pipewire の音量はその後にかかるので手遅れになる。

なお pipewire の音量と ALSA の Capture は連動している。
片方だけ触ると、もう片方に上書きされる（実際に自分でやった）。
**wpctl 側だけで制御する。**

## 音楽

mpd をシステム全体ではなく個人用にし、`mpd.socket` で起動する。

| | |
|---|---|
| 再生していない時 | **0 MB**（ソケット待機のみ） |
| 再生中 | 68 MB |

設計では「mpd 常駐 25MB」と見込んでいたが、ソケット起動にしたことで
**使わなければ 0MB** になった。見込みより良い。

# UI 刷新と声での操作（2026-08-23 夕）

## つまみを捨てて、AI を画面の中心に据えた

最初はミキサーのつまみを並べたが、利用者から「AI OS なのだから
声で言えばやってくれる方がいい」という案が出て、作り直した。
音声認識が動いているのに手で操作する部品を増やすのは筋が悪い。

真ん中に円を置いた。飾りではなく状態そのもので、待・聞・考・話 が
中央の一文字と環の動きで分かる。**声が届いているか分からないまま
話し続けるのが一番困る**ため。

外周に動かない輪郭を一本置いた。中の環だけが回ることで領域が分かり、
全体が落ち着く。輪郭まで動かすと目がちらつく。

## 画面の作りで二度失敗した

**① 左の列に縦積みしすぎた** — 画面は 159桁×18行しかないのに、
固定高さ 19 行ぶんを詰め込み、ツリーが消えた。横に広く縦に短い
画面に縦積みは合わない。

**② dock を同じ辺に複数使った** — お知らせバーと上部バーが両方
y=0 に重なり、計器は Footer の領域に潜り込んでいた。この版の
Textual では同じ辺に複数 dock しても積み上がらない。

どちらも**実機で widget の座標を出して**分かった。見た目の印象で
判断していたら、また外していた。

**③ 円が右にずれた** — 各行の末尾を削っていたため行の長さが揃わず、
中央揃えが一番長い行を基準にしていた。升目を最後まで埋めれば直る。

## 声から操作へ

`chibitaru-act` を作った。「音量上げて」を判定するのに大きな言語
モデルは要らない。語の並びで足りるものは語で片づけ、そうでない
ものだけ Qwen に回す。MYLN を常駐させて重いものは呼ぶ時だけ、
という方針と同じ。

**電源だけは声で実行しない。** 意図は返すが実行はせず、画面の
ボタンを押させる。聞き間違いで電源が落ちるのが一番困る。

### 実際に使って分かったこと

- 「音量を下げて」が「温度を下げて」と書き起こされた。この OS で
  温度は変えられないので、下げられるものは音量しかない。**言い間違い
  として音量に寄せる**。照度・湿度も同様。目的語が落ちた「下げて」も。
- 「もっと下げて」が 10% しか動かず、言い直しても同じだけしか変わら
  ないので伝わっていないように感じた。「もっと」があれば 25% 動かす。
- 計器の棒を数字にした。棒は「だいたい」しか分からず、**いくつなのか
  声で言う時に困る**。電波も dBm から 0〜100% に直した。

## 書き起こしの速度（実測）

| | |
|---|---|
| モデルの読み込み | **102ms** → 常駐させても速くならない（待機 0MB のまま） |
| スレッド 2→4 | 4457→4360ms。2 コアなのでほぼ変わらない |
| `-bo 1 -bs 1` | **出力は一字一句同じで 10% 速い**。採用 |
| 30 秒の塊 | whisper は音声を 30 秒に揃える。短く録っても速くならない |

**4〜5 秒が base モデルでのこの機体の下限。**

## 日本語入力

fcitx5-mozc（45MB）。labwc 0.8.3 が入力メソッドの中継を実装し、
foot が text-input-v3 に対応しているので Wayland のまま通る。

## 電源が切れなかった件（2026-09-04）

画面から電源を切れず、強制終了させてしまった。原因は二つ重なっていた。

**1. polkit が入っていなかった。**
一般利用者の `systemctl poweroff` は polkit の許可が要る。その仕組み
そのものが無かったので、`Call to PowerOff failed: Access denied` で
断られていた。`polkitd` を入れて解決（本体 2.4MB）。
`install/setup.sh` のパッケージにも追加した。

**2. 失敗を握りつぶしていた。**
```python
subprocess.run(["systemctl", "poweroff"], check=False)   # 結果を見ていない
```
断られても画面には何も出ない。押しても何も起きないように見える。
いまは理由をそのまま画面に出す。他の人が入っていて断られた時は、
もう一度押せば `-i` で押し切れる。

**測り方も間違えていた。** `systemctl --dry-run poweroff` は polkit を
通らないので「通る」と出た。実際には通っていなかった。
下のシェルから本物を打って初めて分かった。

> 確かめている最中に、本当に電源が落ちた。polkit を入れた直後に
> Ctrl+Q を二度送ったため。断られる想定だったが通ってしまった。
> **「失敗するはずの操作」を実機で試す時は、成功した場合に何が
> 起きるかを先に数えること。**
